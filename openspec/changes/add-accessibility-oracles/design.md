# Design: Hold accessibility to iOS's own answers

## Context

- pomme builds the tree in `crates/pomme-hle/src/accessibility.rs`
  (`Node`: id, parent, role, label, value, hint, identifier, traits, frame,
  activation point). Hosts get it through `Host::accessibility`.
- `crates/pomme-cli/tests/accessibility.rs` runs a fake screen reader host
  on the accessibility fixture. It checks the tree by hand-written
  expectations, not against iOS.
- The iOS Simulator has **no VoiceOver**. Accessibility Inspector can move
  through elements, but it cannot be scripted. So we need another way to
  get iOS's answer.
- Probes are small apps built with `swiftc` by
  `scripts/swiftui/metrics-simulator.sh`. They have no Xcode project and no
  test target.

## Goals / Non-Goals

**Goals:**

- A recorded, repeatable iOS answer for each accessibility screen.
- Tests for every host path: pomme's tree, the browser's ARIA layer, and the
  Mac's accessibility tree.

**Non-Goals:**

- Perfect agreement on frames for text (pomme uses Inter, iOS uses SF Pro;
  text widths differ). Text frames get a wider tolerance.

## Decisions

### 1. Record iOS's tree with an XCUITest snapshot

XCUITest reads the app through the same accessibility server that
VoiceOver uses. A UI test can take a snapshot of the whole app
(`XCUIApplication().snapshot()`) and walk it: element type, label, value,
identifier, frame, selected, enabled, in the server's order. The runner
prints one line per element:

```
AX 3 button "Tap me" value - id tap traits button frame 20 110 160 44
```

`3` is the depth. The output is saved as `ios26-elements.txt` next to the
probe, like the other recordings.

To run a UI test we need an Xcode project with a UI-test target. We make one
small runner project, generated by a script (as `apps/hello-swiftui` is,
with `make-project.rb`). The runner launches any probe by bundle id and
records it. One runner serves every probe.

Other option: walk UIAccessibility from inside the probe
(`accessibilityElements`, `accessibilityElementCount`). Rejected: for views
that do not override them, UIKit builds the order privately, so the public
API does not show it.

### 2. Reading order needs one check on a real device

The XCUITest order is the accessibility server's order. VoiceOver usually
reads in this order, but it can sort by position too. So, once per fixture,
a person checks the order on a real iPhone with VoiceOver on (swipe right
through the screen) and writes in `ios26-elements.txt` that the order was
checked by hand, with the iOS version and date. If VoiceOver's order differs
from the server's order, we record VoiceOver's order, because that is what
users hear.

### 3. Compare as text, with tolerances

The test turns pomme's tree into the same line format and compares line by
line: role, label, value, identifier and traits must be equal; frames
within 0.5 pt, or within 4 pt for elements whose frame comes from text
width. A difference prints both lines and the place in the tree.

### 4. The browser test uses Playwright's ARIA snapshot

The web build is served by `scripts/serve-web.py`. A Playwright script
(Chromium is installed with Playwright here) opens the page, waits for the
app's first tree, and reads `locator.ariaSnapshot()` of the accessibility
layer. That gives roles and names as the browser exposes them to screen
readers. The test compares it with the expected ARIA mapping of pomme's
tree (written by the Rust side as JSON for the same screen). Then it
presses Tab, Enter and the arrow keys, and checks the app's state changed.

### 5. The macOS test reads the window with the AX API

A small Swift script (`scripts/accessibility/ax-dump.swift`) finds the pomme
window by process id and walks `AXChildren`, printing role, title, value
and frame. It needs the "Accessibility" permission for the terminal, so the
test is skipped (with a message) when the permission is missing.

## Risks / Trade-offs

- [A UI-test runner needs Xcode and code signing for the Simulator] → The
  Simulator accepts ad-hoc signing; write the steps in the script.
- [Text frames differ because of the font] → Wider tolerance for text
  frames only (decision 3).
- [The browser test needs a WASM build, which is slow] → Run it on demand
  (`scripts/test-web.sh`) and in CI later, not in `cargo test`.
- [Many differences at first] → Fix them in this change, one commit per kind
  of difference, so the history shows what changed.
